# Muse 1.4.13 Compatibility Update — Implementation Plan

> **For agentic workers:** Execute inline with TDD. Fingerprint drift is a recorded warning, not a start failure (policy #21, now landed in `src/msp/host.ts`). Do not add a version-specific fingerprint pin test.

**Goal:** Record Muse CLI 1.4.13 evidence and prove inference through the plugin path on both billing paths (subscription and PAYG). The handshake itself is already fixed: policy #21 replaced the exact fingerprint gate with warn-on-drift plus a fail-closed contract check (malformed fingerprint or unsupported envelope version), and a live catalog probe already succeeds with SDK 1.4.12 against CLI 1.4.13.

**Architecture:** No mandatory SDK bump. The host starts against the 1.4.13 CLI with a recorded `fingerprintWarning` under the SDK's additive-optional evolution model. This plan updates compatibility evidence for only the probes actually rerun. An SDK bump to 1.4.13 remains optional and is justified only by a feature the plugin actually uses, never by the fingerprint alone.

**Tech Stack:** TypeScript ESM, npm lockfile, Bun tests, Muse CLI/MSP SDK.

**Spec:** `docs/design.md`; `docs/plans/2026-10-21-opencode-muse.md` Tasks 1, 6, 8, 10, and 15; `AGENTS.md`.

## Global Constraints

- Communicate with Meta only through the official Muse CLI and `@muse-code/sdk` over `muse serve` stdio.
- Never read, copy, cache, log, or transmit Muse credentials or `~/.config/muse` contents.
- Do not reintroduce an exact fingerprint gate or a version-specific pin test; drift warns, malformed/version fails closed.
- Never commit full schema exports; the ledger snapshots are the only versioned schema artifacts.
- Do not claim 1.4.13 support for protocol routes that are not rerun.
- Keep OpenChamber source unchanged.
- Billing-path discipline: `META_API_KEY` takes priority over subscription login. The implementer works on subscription, so every subscription-attributed probe in this plan runs with `META_API_KEY` explicitly unset; otherwise the turn silently bills PAYG. Record which billing path each probe used.

## Baseline (verified 2026-10-24, before this plan)

- System CLI is 1.4.13-R6996.1; repo pins SDK 1.4.12. Under policy #21 the plugin host no longer refuses the handshake: a live `test/probes/msp-catalog.ts` run returned `MSP_CATALOG_PROBED` with three catalog models from the 1.4.13 CLI, served fingerprint `sha256:7fddaf646dbc317e5fcac0785e135eb04df14fbb0db1863089dfd6da21730e5b`, and a recorded `fingerprintWarning` (pinned `sha256:cfdb6d2525601b9bac76584ccb0610ab3a5539b5e4f51141f079b99b39fcb4e0`). That run's billing path was not attributed — Tasks 2 and 3 still need to prove it per path.
- PAYG key itself verified working: `muse usage` reports `No subscription allowance (api_key)`, and a fresh minimal `muse exec --provider meta` turn returned its exact fixed token with exit 0. The plugin needs no auth-code change for PAYG (`src/provider.ts` spawns `muse serve --provider meta` with no auth flags). A text turn through the plugin host on either billing path is still unproven.

## Review Focus

- No package, lockfile, or test change may re-pin the handshake to a single fingerprint.
- The fail-closed contract check (missing/malformed fingerprint, unsupported envelope version) must stay intact.
- Runtime checks must distinguish catalog discovery from actual inference and must not log prompts or generated prose.
- Probe runs must prove which billing path was active (subscription, not stray PAYG via a leaked `META_API_KEY`).
